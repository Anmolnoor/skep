Roadmap

Opinions arrive as code, not promises.

Skep is v1 and single-operator by design. The roadmap follows real usage: what launch users actually hit gets built first, and anything speculative stays parked until there's demand. This mirrors the status table in the README — kept honest on purpose.

Works today

Shipped in v1.0.1, field-tested daily since 2026-07-17.

Sandboxed runs + re-verification
Seatbelt / bubblewrap isolation, independent patch replay with the pinned verify command (G10), full audit trail.
Patch approval
Landing IS the commit — on skep/<task_id>, never main. Workers can never push, pull, fetch, or switch branches.
Chat Queen on every surface
Web, terminal, Telegram / Slack / Discord — with carded mutations and the command deck.
Coding engines
Claude Code, Codex, and Aider adapters, plus the built-in and Ollama workers.
Schedules, digests, MCP, Agent Skills
Recurring runs via skep tick, MCP tools, and skill shelves on the promotion ladder.

Being wired up

In progress now.

PyPI release automation
The tag → CI → GitHub release → PyPI pipeline, hardened release by release.
macOS CI matrix
The Seatbelt path exercised in CI, not just on the dev machine.
Closing the remember→improve loop
Usage signals and recurrence counting so learned templates get sharper with use, not just broader.
Template narrowing + ledger UI
Tighter learned templates and a first-class view of the decision ledger.

Opinions pending code

Built only if launch users repeatedly ask.

Multi-operator / team use
Skep is deliberately single-operator today. Team semantics change the trust model and deserve their own design.
Hosted skep
Cloud sandboxes, GitHub App integration, tenant auth, billing — a later product, not part of the local tool.
Ambient / self-directed learning
The Queen proposing its own work stays behind explicit operator control until the trust engine earns more.
Advanced verification
Test discovery, coverage gating, static analysis layered onto the re-verify step.
